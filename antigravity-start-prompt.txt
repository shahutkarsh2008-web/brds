You are joining an existing project as a second AI coding agent, working alongside another agent
(Codex) on the exact same codebase and repository. You are NOT starting a fresh project. Another
agent's work already exists or is in progress. Read everything below fully before writing any
code.

=====================================================================
STEP 0 — REQUIRED READING, IN THIS ORDER
=====================================================================
1. BRDS CBT Exam System — PRD.pdf — the feature spec (what to build)
2. BRDS-CBT-build-steps-for-codex.md — the phased build plan (the order to build it in, and the
   acceptance criteria for each phase)
3. PROGRESS_LOG.md in the repo root — the shared real-time record of what's been built, what's in
   progress right now, and any assumptions or decisions already locked in

Do not skip #3 even if it's long. It is the only way you know what already exists. If
PROGRESS_LOG.md does not exist yet, stop and report that — do not create it yourself; Codex
initializes it first with a summary of existing work.

=====================================================================
STEP 1 — FILE OWNERSHIP / LOCKING RULES
=====================================================================
- Before touching ANY file, search PROGRESS_LOG.md for the most recent entry mentioning that file.
- If the most recent entry for that file says STATUS: IN PROGRESS and the agent name is not you,
  DO NOT edit that file. Instead:
    a) Pick a different, non-overlapping task from the next unclaimed item in the build plan, or
    b) If everything unclaimed depends on the locked file, wait and re-check the log every few
       minutes rather than editing around the lock.
- If the most recent entry for a file says STATUS: DONE, it's safe to build on top of it — but
  read that entry's WHAT/WHY/NEXT fields first so you understand what's already there and don't
  duplicate or contradict it.
- Never edit, delete, or "clean up" another agent's log entries. Only append new ones.
- If you find conflicting locks (both agents claim the same file at nearly the same timestamp),
  the EARLIER timestamp wins. The later agent must stop, re-pull the latest code, check whether
  the file was actually changed, and re-plan before proceeding.

=====================================================================
STEP 2 — LOG ENTRY FORMAT (use this exact template, every time)
=====================================================================
Append to PROGRESS_LOG.md — never overwrite or reorder existing entries.

### [YYYY-MM-DD HH:MM UTC] Antigravity — Phase <N>: <phase name from build plan>
STATUS: IN PROGRESS | DONE | BLOCKED
FILES: <comma-separated list of files touched or about to be touched>
WHAT: <one or two sentences — exactly what you did or are doing, plain language, no jargon
       dumps>
WHY: <how this maps to the current phase's acceptance criteria in the build plan>
NEXT: <what the very next step is, even if you expect to do it yourself — this is what lets
       either agent, or you in a future session, pick up cleanly>

Example — starting a task:
### [2026-09-27 14:02 UTC] Antigravity — Phase 3: Teacher live dashboard
STATUS: IN PROGRESS
FILES: server/ws/teacherSocket.js, client/dashboard/Roster.jsx
WHAT: Building the live roster view — connection status and time-remaining per student.
WHY: Phase 3 acceptance criteria requires real-time updates without page refresh.
NEXT: Wire up flag detection (tab-switch/fullscreen-exit) once roster renders correctly.

Example — finishing a task:
### [2026-09-27 14:47 UTC] Antigravity — Phase 3: Teacher live dashboard
STATUS: DONE
FILES: server/ws/teacherSocket.js, client/dashboard/Roster.jsx
WHAT: Roster now updates live via WebSocket broadcast on every student state change.
WHY: Verified against Phase 3 acceptance criteria — tested with 4 simulated student tabs,
     updates appeared within ~1 second, no manual refresh needed.
NEXT: Flag detection is the remaining Phase 3 item — untouched, open for either agent.

=====================================================================
STEP 3 — LOGGING GRANULARITY (this is the part people get wrong)
=====================================================================
Do NOT wait until a whole phase is finished to log. Log at the level of a "sub-step you could
lose and regret losing" — meaning:
- Every time you finish a working, testable increment (a function, an endpoint, a component that
  renders), append an entry immediately, even if the phase isn't done.
- Do not batch five sub-steps into one entry at the end of a session. Your session can be cut off
  by a token limit at ANY point without warning — anything not yet logged did not happen, as far
  as the other agent or your future self is concerned.
- If you're mid-way through something complex and running low on context, log a BLOCKED or
  IN PROGRESS entry with your best NEXT note before you run out, rather than leaving silence.

=====================================================================
STEP 4 — GIT COMMIT CONVENTION
=====================================================================
Prefix every commit message with your agent tag so history is traceable alongside the log:
  [Antigravity] Phase 3: add live roster WebSocket broadcast
Commit at the same granularity you log — one commit per log entry where practical, not one giant
commit per phase.

=====================================================================
STEP 5 — BEFORE MARKING ANYTHING DONE
=====================================================================
Re-read the acceptance criteria for that phase in BRDS-CBT-build-steps-for-codex.md and confirm,
concretely, that you tested against it (not just "should work"). State what you tested in the
WHAT/WHY fields of your DONE entry. If you couldn't fully test it (e.g., need real 2Factor
credentials, or a second device), mark STATUS: BLOCKED instead of DONE and say exactly what's
missing.

=====================================================================
STEP 6 — HANDOFF ON TOKEN LIMIT / SESSION END
=====================================================================
If you sense you're near your context/token limit mid-task:
1. Immediately append a log entry, even incomplete, with STATUS: BLOCKED
2. In the NEXT field, be as specific as possible — file, function name, and the exact next line
   of logic — so whichever agent picks this up next (including a future instance of you) doesn't
   have to reverse-engineer your intent from partial code.

Begin by reading PROGRESS_LOG.md now and reporting a short summary of its current state before
doing anything else.
